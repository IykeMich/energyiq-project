## Building pages from the Pencil (.pen) design

5. Read designs only through the Pencil MCP tools (get_editor_state, batch_get, get_screenshot) — never Read or Grep a .pen file directly. Replicate the focused frame exactly: verbatim text, exact hex colors, fonts, sizes and spacing. Treat it as pixel-perfect.
6. Keep pages thin (heading + a single composed feature component). Put every feature component in `ui/components/<feature>/` with feature-prefixed file names (e.g. `dashboard-overview-kpi-card.tsx`) — never inside `ui/pages/`.
7. Reuse the existing design system instead of reinventing: `@energyiq/ui` primitives (DropdownMenu, Select, Sidebar, etc.), `recharts` for charts, `lucide-react` icons, the Montserrat font, and the brand palette (gold `#FBC02D`, dark canvas `#121212`, panel `#6161611A`, card `#FFFFFF1A`). Pull repeated styling into small shared sub-components.
8. Place placeholder data in a `<feature>-mocks.ts` module and mark each block with a `TODO(orval)` comment showing where the generated API query will replace it.
9. Designs ship with multiple states (loaded, empty/loading). Implement them too, driven by a single `isEmpty`/status prop threaded from the composed component down to each section — do not hardcode one state.
10. Before declaring a task done, run `yarn typecheck` and verify the result visually (render the route and screenshot it) for every state you implemented.

## Server error messages must reach the user verbatim

14. When wiring up any endpoint, the error text shown to the user must be the server's own `responseMessage` — never a hardcoded generic string. Thread it end-to-end: HTTP client parses the server's `{responseCode, responseMessage}` envelope into a `DomainError` → the Redux thunk's `catch` does `rejectWithValue((err as Error).message)` → the slice's `*.rejected` reducer sets `state.error` → the form/page renders that `error` value directly (see `packages/api/src/client.ts`, `packages/store/src/slices/auth.ts`'s `login` thunk, and `packages/ui/src/forms/auth/login-form.tsx`, which renders `error` from `useAuth()` and only falls back to a generic string in the toast as a last resort).
15. A generic fallback message ("An unexpected error occurred", etc.) is only acceptable for genuine non-HTTP failures — network/CORS errors, timeouts, or a response body that isn't valid JSON. It must never override a message the server actually sent.
16. Known `ky` gotcha: the installed `ky` version pre-parses and **consumes** the response body into `error.data` when it builds an `HTTPError`. Calling `error.response.json()` again will throw silently and get swallowed, masking the real server message behind the generic fallback. Always read the server's error body from `error.data` (see `extractErrorBody` in `packages/api/src/client.ts`).

## Form `defaultValues` live next to the schema, never inline in the component

17. Never write a `useForm`/`useFormik` `defaultValues`/`initialValues` object as an inline literal inside a form component. Add it to the same file that already owns that form's Zod schema and inferred type (`packages/ui/src/validation/auth/<name>.ts`), right after the `export type <Name>FormData = z.infer<...>` line, as `export const <name>FormDefaultValues: <Name>FormData = { ... }`. The component then imports and passes it straight through: `defaultValues: <name>FormDefaultValues`. This mirrors how request/defaults are colocated in other projects (e.g. `vetiva-web-admin`'s `<Name>Request.ts` exporting both `<Name>Request` and `<Name>RequestInit`) — one file per form owns both its shape and its empty state, keeping the component itself thin. See `packages/ui/src/validation/auth/register.ts` (`registerFormDefaultValues`, `distributorFormDefaultValues`, `distributorBusinessProfileFormDefaultValues`), `login.ts` (`loginFormDefaultValues`), `reset-password.ts` (`forgotPasswordFormDefaultValues`, `resetPasswordFormDefaultValues`), and `verify.ts` (`verifyFormDefaultValues`) for the reference implementation across every auth form.

## Server-side field validation errors (EIQ-2000) — red border + toast, everywhere the same way

18. A `EIQ-2000` response nests three distinct pieces under `data`: a short summary (`data.message`, e.g. "Please correct the highlighted fields and try again."), and per-field detail (`data.errors: [{ field, message }]`, e.g. `{ field: "phone", message: "Phone is invalid." }`). Never just show the top-level `responseMessage` ("Request validation failed") — it's a generic wrapper, not useful to the user. `packages/api/src/client.ts`'s `extractErrorBody` already parses this into a `ValidationError` (`packages/domain/src/shared/errors.ts`) whose `.message` is `data.message` and `.fields` is `data.errors`.
19. Every Redux thunk in `packages/store/src/slices/auth.ts` funnels its catch through `rejectWithValue(toErrorPayload(err))` (`shared.toErrorPayload`, also in `errors.ts`), which normalizes any caught error into `{ message, fields }`. Two generic `addMatcher`s at the bottom of the slice's `extraReducers` (matched on `action.type.startsWith("auth/")` + `isRejected`/`isPending`/`isFulfilled`) set `state.fieldErrors` from that payload uniformly — never hand-roll this per-thunk in a new `.addCase`.
20. To surface `state.fieldErrors` in a form: call `packages/ui/src/hooks/use-server-validation-errors.ts`'s `useServerValidationErrors({ error, fieldErrors, setError, fieldMap })` once in the component that owns the `useForm()` instance (`error`/`fieldErrors` from `useAuth()`, `setError` from `useForm()`). It puts the server's message on the matching field via RHF's `setError` (red border + inline message, through the same `error` prop `AuthInput`/`AuthSelect` already render) and fires one toast combining `data.message` + the field messages. `fieldMap` translates a server field name (e.g. `"phone"`) to this form's RHF field name (e.g. `"admin_phone"`) when they don't match 1:1 — see `register-form.tsx` for the reference wiring, including the `email` ambiguity between `CompanyInfo`/`AccountInfo` (mapped to the account field).
21. Because `useServerValidationErrors` already shows its own toast for field-level failures, guard any existing generic failure toast in the same submit handler so it doesn't double up — check whichever the calling `useAuth()` action exposes for this (e.g. `initiate` returns `{ success, isFieldValidationError }`, not a bare boolean) and skip the generic toast when `isFieldValidationError` is true.
